### Q&A

- transferFrom接口如何使用

    - 需要先授权(approve)，再调用

- ERC721中的授权接口跟ERC20有何不同

    - ERC721针对某个tokenId进行approve,ERC20中approve的是代币的amount

- safeTransfer等带safe前缀的接口提供了什么安全措施

    - 判断to的地址是否实现了IERC721Receiver()方法,防止transfer失败后，代币无法被使用

- delegatecall 跟 call 的区别是什么

    - call调用合约的方法，对于状态变量的修改是被被调用的合约上；delegatecall调用合约的方法，执行的逻辑是被调用合约的方法逻辑，但是对于状态变量的修改是在当前合约上

- 可升级合约的执行流程是什么（user -> proxy -> implementation

    - user <调用> proxy(address) -> proxy <delegatecall> implementation(address)
    - 升级合约时修改proxy delegatecall时调用的address即可

- 代理合约上本身是有存储的，怎么避免跟逻辑合约上的存储产生冲突

    - 冲突产生原因

        - 共享存储空间:代理合约使用delegatecall调用逻辑合约的方法，实际修改的状态变量是在代理合约上
        - 代理合约和逻辑合约对同一存储槽位的理解不同，比如代理合约在slot 0中存储的是implementation，逻辑合约在slot 0中存储的是var1(逻辑合约的状态变量)，所以当逻辑合约修改var1时，会修改slot 0中的存储，而代理合约通过delegatecall修改var1时，实际上修改的是代理合约的slot 0的内容，即implementation，至此冲突产生

- 冲突避免

    - 使用特定的slot来存储代理合约中的状态变量（推荐使用：成熟，安全，EIP-1967定义标准存储槽位，OpenZeppelin 升级插件（自动处理））

    - 在逻辑合约中避免使用已经在代理合约中使用的存储槽位（需要在逻辑合约中手动处理）


- 逻辑合约升级的存储冲突问题

    - 升级合约改变了原有存储变量的顺序或者类型，致使存储槽位的内容发生改变，导致访问/读取数据时发生数据混乱

- 可以在逻辑合约的构造函数中初始化变量吗？为什么

    - 不可以，因为构造函数只有在合约部署的时候调用一次，在代理合约中无法调用，导致逻辑合约构造函数的内容丢失

- 信标代理

    - beacon: 多个proxy通过balacon 获取implementation 的address，升级时，只需要修改beacon中获取implementation的address，即可完成对一批proxy的升级

- 钻石代理

    - 代理合约和逻辑合约是一对多的关系，通过保存选择器 => facet 地址，可以拆分出多个逻辑合约（无限），同时可以针对某个facet进行单独的合约升级

- 最小代理

    - Clone:代理合约和逻辑合约时多对一的关系，多个代理合约指向同一个逻辑合约

#### Uniswap

- 理解什么是AMM，与订单簿的区别

    - 订单簿: 平台所有买单和卖单的汇总，交易者或者机构（做市商）通过低买高卖为市场提供流动性，并获得利润。
    - AMM: 没有订单簿，通过数学公式和流动性池子来自动定价和完成交易
        - 流动性池子: 由LP共同存入两种代币的资金池
        - 定价公式: x * y = k (x + y = k)
        - LP: 将等值的两种代币存入资金池即成为LP（流动性提供者），他们通过交易赚取手续费，并承担无常损失的风险

- AMM的核心算法是什么

    - 恒定乘积公式：x * y = k，x为资金池中代币A的数量，y为资金池中代币B的数量，k为常数，基本保持不变

- 什么是滑点，用户交易时怎么避免滑点过高（三明治攻击？）

    - 滑点：进行交易时，预期价格与实际价格之间的差异
    - 产生滑点原因
        - 市场价格波动
        - 流动性不足
        - 网络拥堵
    - 三明治攻击：针对待处理的交易的恶意行为（例如：买入ETH交易）
        - 抢先交易: 攻击者发现本次交易并以更高的gas费抢跑本次交易，推高池子中ETH的价格
        - 待处理交易被执行：由于池子中ETH的价格已经被拉高，导致本次会以较高的价格买入ETH（巨大滑点），并进一步推高ETH价格
        - 获利交易: 攻击者紧接着卖出ETH（最高价），获取利润，并在交易结束后，池子中ETH价格基本恢复
    - 如何避免
        - 设置滑点容忍度: 超过交易自动失败并回滚
        - 选择流动性高的池子
        - 更换低延迟网络或者在低延迟时间段交易
        - 私有交易
        - 拆分大额订单

- LP的作用是什么

    - 为交易提供流动性
    - 通过定价公式决定资产价格
    - 赚取手续费

- 什么是无常损失？怎么计算

    - 无常损失: 将资产存入资金池产生的收益（本金+手续费）， 与单纯持有这些资产之间的价值差异
    - 初始资金池: 10ETH & 20,000USDC(假设份额占比100%) k = x * y = 200,000
    - 外部市场ETH上涨到4,000USDC，此时套利者进场，底价买入ETH
        - 根据公式，剩余ETH数量为: sqrt(200,000/4,000) = 7.07, 剩余USDC数量为7.07 * 4,000 = 28,280
        - 套利者赚走了2.93个ETH，注入了8,280个USDC
    - 计算资产(假设无手续费产生)
        - 单纯持有: 10 * 4,000 + 20,000 = 60,000
        - 提供流动性后的资产: 7.07 * 4,000 + 28,280 = 56,560
        - 无常损失价值: 60,000 - 56,560 = 3,440
        - 无常损失率: 3,440 / 60,000 = 5.73% 损失了约5.73%的资产

- 集中流动性的优势是什么，怎么实现的

    - 优势
        - 对于LP来说，可以以更少的资金，赚取同样的手续费，并更有针对性的在某个区间内低买高卖
        - 对于交易者来说滑点大幅度降低
    - 实现: 通过引入L(流动性)和tick
        - 定价公式: (x + dx) * (y + dy) = k = L * L
        - 通过tick和L将流动性离散，让用户锁定在自定义价格区间内，同时利用虚拟资产使该区间的资金效率达到最大化

- tick跟价格有什么关系，为什么需要tick

    - 每个tick都对应一个特定的，离散的价格
        - tick本身是一个整数i, P = 1.0001**i(i次方)
    - 原因
        - 管理价格边界
        - 实现高效计算：不同LP有不同的价格区间的流动性，为每个LP计算流动性，效率底下且耗gas，通过tick可以只计算以该tick为边界的流动性即可；并且让系统可以精准计算每个tick区间内的累计手续费，使得LP可以据此公平的分配手续费

- tickspacing跟费率有什么关系，为什么
    - 费率越低，tickspacing越小
    - 波动性越低的资产，越需要精细化管理以追求效率；波动性越高的资产，精细化管理无效且耗gas
